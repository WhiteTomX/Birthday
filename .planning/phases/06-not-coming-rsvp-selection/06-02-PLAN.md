<objective>
Extend the existing RSVP form so guests can decline. Add two radio buttons at the top of the form ("Ich komme" pre-selected, "Ich komme leider nicht"). On submit, route to `/api/not-coming` with `{ name }` for declines or `/api/rsvp` with the full payload for attendance, and show a warm personal German confirmation on success.

Purpose: Deliver the guest-facing decline flow (D-01 through D-05) while leaving the attending experience visually unchanged (default radio pre-selected).

Output: Modified `public/rsvp/index.html` (radio group + field IDs) and `public/script.js` (attendance mode controller, endpoint routing, dynamic confirmation/error labels).
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-06 | Tampering (XSS) | success/decline confirmation rendering in script.js | mitigate | Render guest name only via `textContent` + `createElement` (never `innerHTML` with user input) for both attending and decline messages — established Phase 3 pattern (D-05) |
| T-06-07 | Tampering | client can choose endpoint/payload | accept | Endpoint selection is a client convenience; the server (06-01) independently validates name and hardcodes attendees=0 for declines, so a tampered client cannot corrupt stored data |
| T-06-08 | Information Disclosure | inline submit-error message | mitigate | Error message is a fixed generic German string ("Etwas ist schiefgelaufen…"); no server error detail is surfaced to the DOM |
| T-06-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this plan; plain HTML/CSS/JS, zero dependencies, no build step (PROJECT.md) |
</threat_model>
