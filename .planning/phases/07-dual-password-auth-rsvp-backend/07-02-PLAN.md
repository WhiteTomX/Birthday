<threat_model>
| Threat | Severity | Mitigation |
|--------|----------|------------|
| Password enumeration / timing attack via dual-check ordering | LOW | Both passwords are compared with the same string-equality operation; no early-exit difference reveals which password was tried. Check order (__0 then __1) is fixed and does not leak which slot a guest matched beyond the host index, which is the intended output. No per-character timing dependence beyond JS `===` (acceptable for ASVS L1 on a low-value invite site). |
| X-Host-Ref header injection / spoofing by a client | MED | The middleware constructs the forwarded request's headers and sets `X-Host-Ref` from server-derived `hostRef`. A client-supplied `X-Host-Ref` is overwritten because the middleware always sets it after authenticating. Downstream API (plan 07-03) additionally validates the value is exactly `0` or `1`. The header is set only on the request forwarded to `next()`, never on the Response, so it is not exposed to the browser. |
| Credential leakage via logging or response | HIGH | Password value is never logged, never written to a header, never returned in any response. Only the derived index (0/1) leaves the middleware, via `X-Host-Ref`. `.dev.vars` holds secrets locally and must remain gitignored. |
| 401 bypass — request reaching a protected route without a valid password | HIGH | The only paths returning `next()` are: (a) the unchanged public-route allowlist (`/`, `/index.html`, `/style.css`), and (b) the post-match branch after a password equals `SITE_PASSWORD__0` or `SITE_PASSWORD__1`. Every other path returns `unauthorizedResponse()` (401). Missing/non-Basic auth header still returns 401 before the password check. |
</threat_model>
