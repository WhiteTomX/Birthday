  <files>functions/api/fresh-rsvp.js, tests/phase-9-api.test.mjs</files>

  <behavior>
    - `{ name, attendance: "coming", attendees, drinks }` stores one fresh response with host_ref, group size 1–10, and only valid catalog drink IDs/labels.
    - Missing/overlong names, unknown attendance values, malformed JSON, non-integer or out-of-range `attendees`, invalid drinks, and missing host context return 400 without inserting rows.
    - `{ name, attendance: "not_coming" }` requires only a name and host context and stores no drink associations; a decline with a non-empty drinks array is rejected.
    - Database failures return a generic server error without exposing SQL/runtime details; response plus selected drinks are persisted atomically.
  </behavior>
  <action>Correct the existing handler to follow the Workers `Request`/D1 patterns while enforcing the behavior above. Accept exactly the JSON fields `name`, `attendance`, `attendees` (coming only), and `drinks` (coming only) so the browser/API contract is deterministic; reject coercions such as fractional or partially numeric headcounts instead of relying on permissive `parseInt`. Require host_ref to be exactly 0 or 1 from the auth middleware, use parameterized D1 statements, and persist the RSVP and all drink associations in one D1 batch. Declines must reject a non-empty drink array and store zero group size with no drink links. Do not collect contact information and do not write to the historical `rsvps` table per D-05, D-06, D-08, and D-12.</action>
  <verify>
    <automated>node --experimental-default-type=module --test tests/phase-9-api.test.mjs</automated>
    <fails_when>The process exits nonzero, invalid coming or decline payloads persist, a valid submission changes historical RSVP storage, or a D1 failure exposes internal details.</fails_when>
  </verify>
  <acceptance_criteria>
    - Tests assert valid coming and not-coming responses, host attribution, 1–10 bounds, malformed payload handling, rejection of invalid options, and generic database errors.
    - Decline requests create no drink associations; coming record and selected options are written atomically.
    - The handler has no write path to the historical RSVP table and exposes no database error detail.
  </acceptance_criteria>
  <done>The fresh RSVP endpoint passes the Node built-in tests for both attendance states, boundary validation, and persistence failure behavior.</done>
